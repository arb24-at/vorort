## Purpose and inputs

Plan the site's ownership and each page's reader journey before content generation. Read AGENTS, Project, relevant SEO evidence, actual content/routes and canonical section/block contracts. Use the existing site-wide map and `γ┇Blueprints/Template┇Bilingual Page Blueprint.md`.

## Site-wide map

Show each real page's distinct audience/job, SEO-source IDs, route pair, related destinations and contact journey. Separate existing routes from candidates and unresolved legal/trust locale decisions. Keep priorities in Tasks and business facts in Project. Obtain Aykhan's recorded site-wide approval before page authoring.

## Bilingual page blueprint

Name it `<actual-service-directory>-bp.md`, without a locale suffix. Directory, translation ID and slug can differ: verify all three. Use one bilingual plan, with verified EN/DE content paths and existing Drive file URLs where known; never invent a Drive ID. General pages use their actual source paths rather than a fabricated service folder.

Provide a section overview followed by detailed guidance for each stable instance ID: reader stage, purpose/perception, required meaning/questions, topic/depth, recipe and suggested blocks, flexibility, actions/targets, internal links, media, separate EN/DE SEO coverage and useful length guidance. Localised anchors may differ; map them explicitly. English and German must communicate the same planned information in natural local language. Distinguish target plan from current implementation/adoption.

Plan for recognising a need → understanding practical help → easy contact → optional deeper information. Give enough meaningful context before an early form; do not mandate a fixed section count, scope ID, recognition count, CTA pair or navigation position. Recurring topics need different value at each depth. Required meaning is binding; word ranges and supported block suggestions are not quotas.

## Design choices and approval

Treat Approved sections as flexible palettes. Select, reorder, repeat or omit supported blocks. Check each block's lifecycle separately: parent approval cannot approve an addition. Use actual registered IDs; mark unregistered ideas Proposed with purpose/content shape and no renderer. Show Approved, Experimental and Proposed accurately; manually maintained pills are review snapshots, not authority.

Record every proposed Experimental recipe or block by ID and intended page/locale use. Blueprint approval authorises those trials, not promotion. It does not silently expand an existing production permission. A worker must register the exact trial before rendering it; see Implementation.

Submit each blueprint when ready, without waiting for every other page. Record approved version, Aykhan decision reference and outstanding dependencies only after actual approval. Major later changes to intent, scope, essential interaction or journey require a new review; compatible refinements and ordinary wording do not. Never mark a blueprint approved on Aykhan's behalf.
